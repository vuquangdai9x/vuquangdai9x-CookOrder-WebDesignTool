## Chapter: Starting from Scratch

Covers how to begin a design without getting stuck. Start with one concrete feature (not the app "shell"/nav layout) since layout decisions are unanswerable in the abstract before any real content exists. Delay detail: work in low fidelity first (literally pencil/paper or grayscale) so spacing, contrast, and hierarchy carry the design instead of color and ornament, and don't over-invest in disposable sketches. Avoid designing more than the next working increment ("don't design too much") — build one small feature fully, ship it, learn from its real edge cases, then design the next piece; be a "pessimist" and never imply functionality (like an attachments UI) that isn't actually going to be built soon, because a half-implied feature blocks shipping the simpler, complete version. Personality (the emotional tone of a design) is set by a small number of concrete levers: typeface choice (serif = elegant/classic, rounded sans = playful, neutral sans = quiet/utilitarian), color (blue = safe/familiar, gold = premium, pink = fun/light), border radius (sharp corners = formal/serious, large radius = playful, small/none = neutral) — and consistency in these choices matters more than any single choice. Language/microcopy tone (formal vs. casual wording) shapes personality as much as visuals do. Finally, "limit your choices": design decisions made from an unconstrained infinite palette (any hex code, any pixel value) are exhausting and produce inconsistent results, because there's rarely one obviously correct answer; pre-defining constrained systems (a fixed color palette, a fixed type/spacing scale) turns every subsequent decision into an easy pick from a short list, using a comparison technique — take a guess, compare the option above and below it, discard whichever direction looks worse, repeat.

**Game UI bridge**: Prototype one game screen (e.g. the inventory grid) fully in grayscale/wireframe before styling the whole menu shell — trying to nail nav layout, HUD chrome, and art style all at once before any screen works is a common trap. Treat personality levers (font, corner radius, palette, in-fiction vs. plain copy) as a single coherent "kit of parts" decision made once per game, then applied consistently across every menu/HUD/store screen — mixing a rounded playful font with sharp military-serious icon shapes reads as unintentional. Predefine constrained systems (a locked spacing scale, a locked color ramp, a locked icon-size scale) before UI artists start producing individual screens, so decisions like "is this padding 12px or 14px" never have to be re-litigated screen by screen.

## Chapter: Hierarchy is Everything

Visual hierarchy — how important each element looks relative to others — is presented as the single biggest lever for making a UI feel "designed," more so than color or ornament. Font size alone is a weak/blunt hierarchy tool (it forces primary text too large and secondary text too small); font weight and color/contrast are better levers — bold or dark for primary content, mid-grey for secondary, light grey for tertiary, and generally two font weights (regular + one heavier) cover most UI needs. Grey text loses its de-emphasizing effect on colored backgrounds (reduced-opacity white looks washed out/faded instead); the fix is to hand-pick a new color at the same hue as the background, adjusted in saturation/lightness, rather than faking it with opacity. "Emphasize by de-emphasizing": when an element still doesn't stand out despite styling it more, mute its competing neighbors instead (e.g. soften inactive nav items rather than further bolding the active one; drop a sidebar's background color rather than intensifying the main content area). Labels should be a last resort for presenting data — format and context (an email pattern, a price with a $, a name's position in a card) usually communicate what a value is without a label; when a label truly is needed, either fold it into the value ("12 left in stock" instead of "In stock: 12") or visually subordinate it (smaller, lighter, lower weight) unless the user is specifically scanning for the label itself (e.g. spec sheets), in which case the label can outrank the value. Visual hierarchy should be decoupled from HTML/semantic document hierarchy — an h1 used for a "page title" label doesn't have to be visually huge just because browsers default h1 to large type; pick markup for semantics/accessibility and style independently for the actual visual weight needed. Weight and contrast trade off against each other: heavy elements (bold text, solid icons) can be visually balanced against lighter neighbors by reducing their contrast (softer color), and low-contrast elements (thin borders) can be strengthened by adding weight (thicker stroke) instead of darkening color. Button/action styling should follow an importance hierarchy, not pure semantics: one true primary action gets a solid high-contrast treatment, secondary actions get outline/low-contrast treatment, tertiary actions look like plain links — and a destructive action should only get "big red bold" styling when it actually is the primary action of that specific screen (e.g. inside a confirmation step), not by default everywhere it appears.

**Game UI bridge**: HUD elements (health, active objective, target reticle) need font weight/color/contrast doing the hierarchy work, not just size — an oversized health number and a barely-visible ammo count is exactly the failure mode this chapter warns against. Apply "emphasize by de-emphasizing" to HUD clutter: if a critical alert doesn't pop, first try dimming/softening the ambient HUD elements around it rather than making the alert bigger and louder. Inventory/shop item data (rarity, price, stats) should lean on format and position over redundant labels — a colored border already says "rare," a "$" prefix already says "price," so a label is often pure noise. Store/menu CTAs should follow the primary/secondary/tertiary button hierarchy strictly: one obvious "Buy"/"Confirm" per screen, secondary actions as outline buttons, and "Cancel"/"Skip" as link-styled text — with destructive actions (delete save, refund purchase) only getting alarming red-bold treatment at the actual confirmation step, not on the initial button.

## Chapter: Layout and Spacing

Argues white space should be treated as something you start with too much of and remove, not something you add in small increments until "good enough" — the incremental-add approach reliably under-shoots. Dense, information-packed UIs (dashboards) are a legitimate deliberate exception, not a default. A spacing/sizing system should be built on a non-linear scale: small values need fine-grained steps (12px→16px is already a 33% jump) while large values can jump in big absolute increments without feeling different (500px→520px is imperceptible), so no two scale values should sit closer than roughly 25% apart; a practical approach is picking a base (commonly 16px) and building a hand-tuned scale around it rather than a naive "everything is a multiple of 4px" rule. Elements don't need to fill all available screen width just because the canvas or another section is wide — give an element only the width its content needs, and consider designing on a deliberately narrow canvas (e.g. ~400px, mobile-first) to force appropriately compact decisions, then scale up. Where a narrow element feels unbalanced against a wide layout, splitting it into columns (rather than stretching it) can use the space without hurting usability. Grid systems (e.g. 12-column) are useful defaults but shouldn't be treated as mandatory for every element — sidebars, cards, and other components with an optimal fixed width should get a fixed/max-width instead of a fluid percentage, because a percentage-based sidebar becomes wastefully wide on big screens and cramped on small ones; give components a max-width and let them shrink only once the viewport actually requires it, rather than snapping between fixed grid-column counts at each breakpoint (which can paradoxically make an element narrower on a "bigger" breakpoint). Relative sizing (e.g. defining a heading as 2.5em relative to body text) breaks down across screen sizes — the ratio that looks right on desktop (2.5x) is usually wrong on mobile (should be closer to 1.5-1.7x); big elements need to shrink faster than small ones as screens shrink, so properties should be tuned independently per context rather than mathematically derived from one base value — this applies within a single component too (e.g. button padding shouldn't be purely proportional to font size; padding should get relatively more generous at large sizes and relatively tighter at small sizes for the size difference to actually read). Finally, ambiguous spacing (equal gaps above and below related items, or equal gap between bullets and their own line-height) makes it unclear which elements are grouped; the fix is to always make the gap between groups larger than the gap within a group, in both vertical and horizontal layouts.

**Game UI bridge**: Menu screens (inventory, skill tree, settings) benefit from starting "too spacious" and tightening, rather than cramming controls together by default — cramped menus are one of the most common indie/game-jam UI complaints. Build one locked spacing scale (icon padding, card gutters, section margins) shared across every menu/HUD screen so a UI artist never hand-picks arbitrary pixel gaps per screen. Don't force HUD elements or menu panels to stretch full-width just because the screen is wide — a settings list or dialogue box should use its optimal fixed width and let the rest of the screen breathe, especially on ultrawide monitors. Watch for relative-sizing bugs when scaling HUD elements between resolutions/aspect ratios or console-to-handheld: a health bar sized proportionally to a 4K desktop layout will not simply "scale down correctly" on a Switch or Steam Deck screen without independent tuning. Use a visibly larger gap between inventory item groups/categories than within a group's own grid so players can tell where one category ends and the next begins without relying on a divider line.

## Chapter: Designing Text

Recommends defining a small, hand-picked type scale rather than picking font sizes ad hoc — mathematically "pure" modular scales (ratios like 4:5 or the golden ratio) are elegant but tend to produce awkward fractional pixel values and too few practical in-between sizes for interface work, so a hand-crafted scale (values chosen by eye, aligned to the spacing scale) works better for UI than for long-form editorial text. Font sizes should be defined in px or rem, not em, because em is relative to the parent's computed size and nested em values silently drift off the intended scale. For font selection without deep typography expertise: default to a safe, neutral system-font-stack sans-serif if unsure; treat "fewer than 5 weights available" as a mild red flag for typeface quality; avoid condensed/short-x-height display faces for body/UI text since those are optimized for large headline use, not small-size legibility; lean on font popularity rankings and "steal" font choices from admired, well-designed sites as legitimate shortcuts while your typographic eye develops. For paragraph text, keep line length to roughly 45-75 characters (≈20-35em) for readability — going wider is possible but risky — and this constraint should hold even inside a wider content area shared with images (mixed-width layouts read as more polished, not less). When mixing font sizes on one line (e.g. a card title next to smaller action links), align by baseline rather than vertical-center, since baseline alignment matches how the eye naturally reads text and avoids the subtly "off" look of centered mixed sizes. Line-height should scale inversely with font size (large headlines can use line-height near 1, small body text needs more like 1.5) and proportionally with line length (wider paragraphs need taller line-height, up to ~2, so the eye can relocate the next line after a long horizontal jump). Not every link needs full-strength link styling — in link-dense interfaces (as opposed to prose), de-emphasize most links to weight/color changes only, reserving underline/hover-reveal treatment for truly secondary/ancillary links so the important ones aren't drowned out. Left-alignment is the readable default for most languages; centered text only works for short (≤2-3 line) independent blocks — a body of center-aligned text that runs long should either be left-aligned or edited shorter. Numbers in tabular contexts should be right-aligned so decimal points line up for scanning. Justified text needs hyphenation enabled or it produces ugly word-gaps. Letter-spacing is generally best left at the type designer's default, with two practical exceptions: tightening letter-spacing on headline text set in a body-optimized typeface (to mimic a purpose-built display face), and widening letter-spacing on all-caps text (since capital-only text loses the ascender/descender shape variety that normally aids letter recognition).

**Game UI bridge**: Define one small type scale (5-7 sizes) shared by all UI text — dialogue, tooltips, HUD numbers, menu headers — instead of letting each screen introduce its own font size; this is one of the highest-leverage, lowest-effort consistency fixes available to a small team. Favor a neutral, highly legible sans-serif for body/tooltip/stat text even if a stylized display font is used for titles/logos — a beautiful fantasy-styled font at 14px in a tooltip is a common readability failure. Use font weight and color rather than size alone to separate primary stat numbers from secondary flavor text in tooltips and item cards. Watch line-height and line-length together when localizing UI text — German or Finnish strings run longer than English, and a line-height tuned for short English labels can crowd wrapped translated text. All-caps UI labels (common in HUD callouts, achievement banners) need extra letter-spacing to stay legible, especially at small HUD sizes on a TV/console viewing distance.

## Chapter: Working with Color

Recommends thinking and defining colors in HSL (hue/saturation/lightness) rather than hex/RGB, since HSL's components map to how people actually perceive color (hue = position on the color wheel; saturation = vividness, with 0% being grey; lightness = closeness to black/white, with 50% being the pure hue) — note HSL's "lightness" is not the same axis as HSB's "brightness," and only HSL is natively usable in CSS. A real UI needs far more colors than a 5-color "brand palette" generator produces: roughly 8-10 grey shades (UI is mostly grey — text, backgrounds, panels, borders — and 3-4 shades are never enough once you need something between two existing steps), 5-10 shades each of one or two primary/brand colors (for buttons, active states, tinted backgrounds, and darker text-safe variants), and multiple accent colors (for highlighting, semantic states like destructive/warning/success, and category/tag differentiation) — a complex product can reasonably need ~10 colors × 5-10 shades each. Shades should be defined once, up front, as a fixed named ramp (not generated on the fly with "lighten"/"darken" functions, which produces dozens of near-duplicate colors) — the recommended process is: pick a base/mid shade (good rule of thumb: a shade that would work as a button background), pick the darkest shade (usually for text) and lightest shade (usually for tinted backgrounds) by eye using real contexts like an alert component, then fill in the gaps by repeatedly bisecting (pick the shade halfway between two known shades) until you have ~9 steps — this is a systematic starting point, not a rigid formula; hand-tweaking afterward is expected and fine. A pitfall: saturation's visual impact weakens as lightness approaches 0% or 100%, so naively lightened/darkened shades look washed out — compensate by increasing saturation as lightness moves away from 50%; a related, more advanced trick is that every hue has an inherent "perceived brightness" (yellow/cyan/magenta read brighter than red/green/blue at equal HSL lightness), so a color can be made to feel lighter or darker by rotating its hue a small amount (20-30° max) toward the nearest bright or dark hue instead of only adjusting the lightness slider, which better preserves color intensity. "Grey" doesn't have to be neutral — most UI greys actually carry a slight saturation, which is what makes a grey read as "cool" (blue-tinted) or "warm" (yellow/orange-tinted); this saturation should also be preserved consistently across the whole grey ramp's lighter and darker steps, not just the middle. For accessibility, WCAG recommends a 4.5:1 contrast ratio for normal text and 3:1 for large text; meeting this on colored backgrounds is harder than plain black-on-white — "flipping the contrast" (dark text on a light-tinted version of the color, instead of light text on a dark/saturated version of the color) is often both more accessible and visually calmer/less attention-grabbing than expected; for colored text on a colored background specifically, rotating the text's hue toward a brighter hue (rather than pushing lightness toward white) can hit contrast targets while staying colorful. Finally, never rely on color as the sole signal (e.g. red/green for bad/good) since colorblind users can't distinguish it — pair color with a redundant channel like an icon, and for things like multi-line charts prefer contrast (light vs. dark) differences over hue differences, since light/dark reads reliably across most forms of color blindness.

**Game UI bridge**: Build one HSL-based color system (greys + 1-2 primary/faction colors + semantic accents for buy/sell/rare/error) with 8-10 defined shades each, shared across HUD, menus, and store screens — this is the color-system equivalent of the type-scale/spacing-scale advice and prevents "37 near-identical blues" across a UI art pass. Never use color alone to signal rarity tiers, buff/debuff states, or faction allegiance — pair every color-coded status with an icon or shape so colorblind players (a meaningful fraction of any player base) aren't locked out of reading the HUD; this is a frequently-cited accessibility gap in shipped games. For readability of stat text or damage numbers over busy in-game backgrounds, favor the "flip the contrast" and hue-rotation techniques over simply cranking opacity, which tends to look washed out on top of colorful game art.

## Chapter: Creating Depth

Explains how to fake real-world lighting cues to make flat 2D UI elements read as raised or inset, built on one governing rule: light comes from above, so a raised surface's top edge (angled toward the light) should be lighter, and its bottom edge (angled away, or blocked by the raised lip) should be darker/shadowed — and the reverse for inset/recessed surfaces. Practically: for a raised element (e.g. a button), since the viewer is assumed to look slightly downward, only reveal the top edge highlight (a hand-picked lighter color, not translucent white, applied as a thin top border or small inset shadow) and only cast the shadow below the element (a small, sharp-edged, minimally-blurred dark shadow) — the element blocking light below it, not surrounding it, is what reads as "raised." For an inset element (e.g. a text input, checkbox, or "well"), the visible edge flips: a light bottom lip (facing upward) and a small dark inset shadow pressed toward the top (light being blocked from fully reaching the recess). This effect should be used with restraint — chasing photorealism produces a busy, distracting UI; a little cue goes a long way. Beyond binary raised/inset, shadow size can convey a full elevation scale on a virtual z-axis: small tight shadows = barely raised (subtle, e.g. a button), medium shadows = clearly floating above content (e.g. a dropdown), large soft shadows = very close to the user and demanding full attention (e.g. a modal) — defining a fixed 5-step shadow scale (smallest and largest first, then filled in between) mirrors the spacing/type/color scale advice elsewhere in the book. Shadows can also communicate live interaction state, not just static position — e.g. growing a shadow when a user picks up a draggable list item (it visually "pops" forward), or shrinking/removing a button's shadow on click (it visually presses into the page). A well-crafted shadow is often actually two stacked shadows doing different jobs: a larger, softer, more offset shadow simulating the general cast shadow from a direct light source, plus a tighter, darker, less-offset shadow simulating the "contact shadow" where ambient light can't reach right at the object's edge — and that tight contact shadow should fade out as an element's elevation increases (very close to invisible at the highest elevation level), matching how it behaves with physical objects. Even "flat design" (no shadows/gradients at all) can still convey depth: lighter shades read as closer, darker shades read as further away (so lightening an element relative to its background reads as raised, darkening it reads as inset), and short, hard-edged, zero-blur offset shadows ("solid shadows") can suggest elevation while staying visually flat. Finally, deliberately overlapping elements (letting a card straddle two background sections, or letting a component slightly overhang its parent container) is an effective, simple way to create a layered feeling; when overlapping photos/images specifically, giving each image a thin border matching the page background prevents them from visually clashing/bleeding into each other.

**Game UI bridge**: A fixed 5-step shadow/elevation scale is directly useful for layering game UI panels — tooltip-over-card-over-panel-over-HUD needs a consistent z-axis language so a modal always reads as "closer" than the tooltip beneath it, not the reverse. Use shadow/highlight state changes as a cheap, readable feedback layer for interactive UI: a card lifting (bigger shadow) on hover/focus and pressing down (shadow shrinks or disappears) on click gives players the same tactile confirmation button-press animations aim for, without needing a full animation pass. For flat/stylized art directions where realistic shadows would clash, lean on the "lighter = closer, darker = further" color trick and hard-edged offset "solid shadows" to keep buttons and cards feeling clickable without breaking the flat aesthetic.

## Chapter: Working with Images

Bad photography undermines an otherwise good design, so the practical options are hiring a professional or using high-quality stock/free photo resources — placeholder images with a plan to "swap in real photos later" reliably fails because layouts get tuned around whatever placeholder was used. Background images with text overlaid on them create an inherent contrast problem, since real photos have both light and dark regions, so no single text color reads well everywhere; the fix is to reduce the image's dynamic range before adding text, via one or more of: a semi-transparent black or white overlay (tones down highlights or lifts shadows, simple but affects the whole image uniformly), directly lowering the image's contrast (more targeted, but needs a brightness compensation pass afterward), colorizing the image (lower contrast, desaturate, then apply a solid color fill in multiply blend mode — also useful for matching a photo to brand colors), or adding a soft, non-offset text shadow (a "glow" rather than a drop shadow) as a way to preserve more of the image's natural dynamics while still guaranteeing legibility. Every image type has an intended display size baked into how it was produced, and violating that in either direction causes visible quality loss: small icons (drawn crisp at 16-24px) look chunky/disproportionate when blown up to 3-4x size — if only small icons are available, wrap them in a larger background shape rather than upscaling the icon itself; conversely, icons/logos meant for large display look mushy when shrunk far below their intended size (the extreme case being a detailed logo crushed down to a 16px favicon) — redraw a deliberately simplified version at the target small size instead of relying on the browser/renderer to auto-shrink it well. The same intended-size problem applies to screenshots: shrinking a full desktop screenshot to fit a small marketing tile crushes its UI text below legibility — better options are capturing at a smaller source resolution to begin with (so less shrinking is needed), showing only a cropped partial screenshot, or substituting a simplified schematic redraw (boxes/lines standing in for real UI) if a full screenshot must fit a tight space. User-uploaded images (avatars, listing photos) can't be quality-controlled the way curated photography can, but layout damage can still be contained: force uploads into a fixed-aspect-ratio container (CSS background-size: cover is the easy web implementation) so wildly varying image dimensions don't break grid layouts, and prevent a user's image bleeding into a similarly-colored page background by adding a subtle inner shadow (looks better than a hard border, which tends to visually clash with whatever colors happen to be in the uploaded image) or a semi-transparent inner border as an alternative.

**Game UI bridge**: Player-facing marketing/store screenshots and character-portrait thumbnails need the same fixed-container + cover-crop treatment as web user-avatars — a store carousel that lets uploaded/varying-aspect promotional art break its grid looks unpolished fast. Icon assets (ability icons, item icons, HUD glyphs) should be authored at their actual display size, not auto-scaled from one master icon sheet — an ability-bar icon drawn for a 96px inventory slot will look chunky blown up for a big skill-tree node, and a detailed icon crushed down to an 8px minimap pip will turn to mush, so minimap/HUD-scale icons typically need their own simplified redraw. For any UI with a background photo/render behind text (loading screens, character-select splash art, store banners), apply the overlay/contrast-reduction/text-shadow techniques rather than hand-picking one text color and hoping it works against every piece of concept art dropped behind it.

## Chapter: Finishing Touches

A grab-bag of low-effort, high-impact polish techniques for developers without deep visual-design or illustration skill. "Supercharge the defaults": replace generic bullets with meaningful icons (checkmarks, or something content-specific like a padlock for security features), visually "promote" pull-quotes/testimonials into a distinct styled element rather than plain body text, give links custom styling beyond the browser default (weight/color change, or a thick offset underline), and restyle default checkboxes/radio buttons with a brand color — small changes to browser/OS defaults read as disproportionately more "designed." Accent borders (a solid color bar/stripe) are a low-skill way to inject brand color and visual interest without any illustration ability — usable across a card's top edge, an active nav item, the side of an alert, under a headline, or across an entire page header. Backgrounds can be "decorated" cheaply to break up an otherwise plain design: a flat color change on a panel or section (or a subtle gradient between two hues no more than ~30° apart on the color wheel for an energetic-but-controlled look), a low-contrast repeating pattern (doesn't need to cover the whole area — a pattern confined to one edge works too), or a simple geometric shape/illustration/map placed in a specific spot — contrast should stay low in all these cases so the decoration doesn't compete with real content. Empty states (a list/section with zero items, before any user-generated content exists) are commonly neglected but are often a new user's literal first impression of a feature — treat them as a priority, not an afterthought: use an illustration/image to make the empty screen feel intentional rather than broken, emphasize the call-to-action that gets the user to create their first item, and hide supporting chrome (tabs, filters, sort controls) that has nothing to act on yet. Borders aren't the only (or always best) way to separate adjacent elements — alternatives that feel less busy/cluttered include a subtle box-shadow outline (works best when the element's background differs from the page background), simply giving adjacent regions two different background colors, or just adding more spacing between them; if background-color separation is already present alongside a border, try removing the border first. Finally, "think outside the box": default assumptions about how a component "has to" look are often just convention, not a real constraint — a dropdown doesn't have to be a plain link list (it can use sections, columns, icons, and supporting text), a table column doesn't have to isolate one data field per column (related fields can combine into one richer, hierarchical cell, and cells can include images/color instead of only plain text), and a set of radio buttons can become selectable cards when the choice is important enough to deserve more visual weight.

**Game UI bridge**: Restyled default browser checkboxes/radios have a game-UI parallel in settings menus — reskin toggle switches, sliders, and radio-style option pickers with the game's actual color/style kit rather than shipping unstyled default engine-UI widgets, which is a common "looks like a prototype" tell. Accent-color stripes are a cheap way to differentiate item rarity tiers, faction affiliation, or active-tab state on card-based UI (inventory, loadout, deck-builder) without needing custom art per variant. Empty states deserve real design attention in games specifically because they hit constantly — a fresh save's empty inventory, an un-started quest log, a guild-less social tab — and a blank list with no guidance reads as broken rather than "not started yet"; pair it with a clear next action (go fight, go craft, go find a guild). For loadout/ability-select screens, consider selectable cards instead of plain radio-button lists when the choice (weapon, class, difficulty) is consequential enough to warrant visual weight and preview information.

## Chapter: Leveling Up

Short closing chapter offering two ongoing practice habits for continuing to improve past the book's specific tactics. First, actively look for design decisions the observer wouldn't have thought to make themselves when studying admired interfaces (unconventional inversions, unexpected control placement, small typographic surprises) — treating those "I wouldn't have thought of that" moments as the actual unit of learning, more valuable than admiring a design in general terms. Second, and more effective, is deliberately rebuilding a liked interface from scratch without inspecting its underlying code/files — the friction of noticing your version looks subtly different than the original, then diagnosing why, is what surfaces specific transferable techniques (e.g. tightened heading line-height, letter-spaced caps, layered shadows) that passive observation misses.

**Game UI bridge**: The "rebuild it yourself" practice applies directly to a UI/UX team studying competitor games — recreating a rival's inventory grid or HUD layout pixel-for-pixel (rather than just screenshotting it for a mood board) is what actually surfaces the specific spacing, weight, and hierarchy choices worth adopting, and is a fast, low-cost way to build a team's collective visual-design intuition before a new project's UI style is locked.
